# 02. 48 小時運行結果

本文件記錄 CSIE5377 Starter Project 單次連續無人值守運行的實測行為，觀測視窗自
2026-09-17 00:49:32 起算，長度為整整 48 小時（172,800 秒）。內容涵蓋視窗內
的抓取統計、狀態碼與延遲分布、失敗原因分類、吞吐量隨時間的衰減與成因分析，
以及防爬蟲陷阱上限的實際效果。文中視窗彙總取自 `results/summary-48h.json`，
每小時吞吐量取自 `results/throughput-hourly.csv`；狀態碼、延遲百分位與失敗
原因分類由 `output/results_clean.jsonl` 重新計算，佇列、並發與丟棄連結等時序
指標取自 `output/metrics_log_clean.csv`。

## 2.1 運行設定

```bash
# 48 小時無人值守運行的完整啟動指令
python -m crawler.main \
  --seeds seeds.txt \
  --follow-links \
  --concurrency 50 \
  --queue-maxsize 50000 \
  --max-pages-per-domain 20 \
  --max-runtime-hours 48 \
  --checkpoint-interval 300
```

種子清單 `seeds.txt` 含 1,000 個網址：16 個樞紐頁面，加上 984 個從 Tranco
排名分層抽樣而來的網域，產生方式見
[01-system-design.md](./01-system-design.md) §1.4.2。統計視窗為
2026-09-17 00:49:32 至 2026-09-19 00:49:32，整整 172,800 秒。

### 2.2.1 狀態碼分布

以 1,264,115 次抓取為分母：200 佔 94.81%、404 佔 1.83%、403 佔 1.57%、
連線失敗（無狀態碼）佔 1.10%、429 佔 0.25%；其餘 4xx 與 5xx 合計 4,515 次，
另有非標準狀態碼 999（30 次）與 901（5 次）共 35 次，三者合計 4,550 次、
佔 0.36%。

### 2.2.2 延遲百分位

以成功抓取為母體（n = 1,199,676）：p50 = 868.5 ms、p90 = 2,495 ms、
p99 = 6,019 ms、最大 14,381 ms。連線失敗的 13,860 次與被 `robots.txt`
擋下的 23,179 筆 `elapsed_ms` 均為 0，不列入此母體。

這個 p50 是整段視窗的聚合值，不代表延遲全程穩定：逐小時的 p50 由第 1 小時
的 528.5 ms 升到第 36 小時的 1,181.8 ms，視窗結束時為 941.9 ms（見 §2.3.2）。

## 2.3 吞吐量衰減

吞吐量在 48 小時視窗內衰減約 9.2 倍；在視窗結束之前，吞吐量早已遠離高峰。
衰減是連續而平滑的，沒有出現任何一次卡死，但 worker pool 並未撐完全程：
50 個 worker 之中有 46 個在視窗內永久停止（§2.3.3）。

### 2.3.1 實測衰減

| 時點 | 每小時抓取次數 |
|---|---|
| 第 5 小時（高峰） | 67,614 |
| 第 12 小時 | 50,095 |
| 第 24 小時 | 19,968 |
| 第 36 小時 | 8,066 |
| 第 48 小時（視窗結束） | 7,354 |

第 1 至 48 小時加總為 1,264,115 次，與 §2.2 的抓取次數完全一致。

![48 小時視窗內每小時抓取次數](./rsc/throughput-48h.png)

圖 3　每小時抓取次數。第 5 小時達到高峰後持續下滑，視窗最後一小時只剩
7,354 次。過程中有 12 次小時對小時的小幅回升，但從未出現斷崖。

換算成速率：高峰的 18.78 次/秒 降到視窗結束時的 2.04 次/秒，即 48 小時
視窗內衰減 9.2 倍。

因此 §2.2 的 7.32 次/秒 是一個「健康階段與瀕死階段的混合平均」：視窗結束
時的實際速率只有約 2 次/秒，引用單一平均值會明顯高估系統的穩態能力。

### 2.3.2 成因：有效並發塌陷，而非網路變慢

網路端確實變慢了，但幅度遠不足以解釋 9.2 倍。取第 3–8 小時與第 40–48 小時
都成功抓取過的 996 個網域配對比較，逐網域中位數由 813 ms 升到 1,048 ms，
即 1.29 倍。

真正塌陷的是有效並發：`crawler_inflight_requests` 的小時均值由第 6 小時的
高峰 25.94 降到視窗結束時的 3.05（上限為 `--concurrency 50`，見
[01-system-design.md](./01-system-design.md) §1.3）。同一期間
`crawler_queue_depth` 在運行開始約 14 分鐘後便觸及
`--queue-maxsize 50000` 的上限，視窗內 90.4% 的取樣維持在 49,999 以上
（§1.4）；48 小時內因佇列已滿而被丟棄的連結累計 65,355,760 條
（`crawler_links_dropped_queue_full_total`，見 §1.4.1 與 §1.9）。可派工的
網址從不匱乏，瓶頸在 worker 這一端。

![並發請求數與佇列深度](./rsc/concurrency-queue-48h.png)

圖 4　並發請求數（上）與佇列深度（下）的小時均值。待爬佇列自始至終貼著
上限，但實際在飛的請求數持續下滑。

以 Little's law 檢驗：λ·W ÷ L 在全視窗為 0.808（λ = 7.3155 次/秒、
W = 1.1927 秒、L = 10.7954），48 個小時各自比值的平均為 0.813 ± 0.035。
比值穩定地小於 1 而非等於 1，這個缺口本身就是量測結果而不是誤差：
`metrics.INFLIGHT.inc()` 排在 `await rate_limiter.acquire(url)` 之後
（`worker.py:48-49`），因此 worker 等待每網域閘門的時間既不計入
`crawler_inflight_requests`，也不計入 `elapsed_ms`。兩個量測區間都看不到
這段等待。

視窗結束時的迴圈拆解因此是：存活的 4 個 worker 合計 2.04 次/秒，每個
worker 約 1.96 秒完成一次迴圈，其中 1.49 秒（76.15%）落在量測區間之內。

### 2.3.3 主因：worker 靜默死亡，有效並發由 50 降到 4

![worker 存活曲線與第 48 小時的 inflight 分布](./rsc/worker-survival-48h.png)

圖 5　每 30 分鐘的 inflight 天花板與以二項分布最大概似估計的存活 worker
數（左），以及第 48 小時 inflight 取樣的分布與兩個競爭模型（右）。

**已量測的部分。** inflight 的 30 分鐘天花板先由 28 升到 43（第 2 至 3
小時），之後一路下滑到 4；下滑途中有 8 次小幅回升，但再也沒有回到早期
水準，第 37 小時之後的最後 11 小時沒有任何一格超過 4。第 48 小時的 718 次
取樣分布為 {0:1, 1:31, 2:144, 3:300, 4:242}，與 Binomial(4, 0.76) 逐格
吻合；若此時仍有 50 個 worker 在跑，同均值的 Binomial(50, 0.061) 應該出現
134 次超過 4 的取樣，實測為 0 次。以同樣方法估計的存活數為 50 →
35（第 12 小時）→ 12（第 24 小時）→ 5（第 36 小時）→ 4，指數存活曲線的
R² 為 0.947，線性只有 0.876。

**推論的部分。** 上述資料足以排除所有「卡在量測區間之內」的解釋——連線槽
洩漏或 `store.record()` 的鎖都會把 gauge 釘在高位，而實測是低位。剩下的
可能是 worker 已經結束，或是永久卡在 `INFLIGHT.inc()` 之前；前者證據強得
多：`worker()` 的迴圈只有 `try`／`finally` 而沒有 `except`，`main.py:128`
又以 `return_exceptions=True` 收尾，因此任何逸出的例外都會讓該 worker
永久退出，而且不留下任何記錄。三個未受保護的呼叫點已在本機對真正的模組
重現出 `ValueError: Invalid IPv6 URL`（`linkextract.py:39` 的 `urljoin`、
`worker.py:97` 的 `normalize_url`、`worker.py:32` 與 `:98` 的
`domain_of`）。但這次運行究竟是哪一個例外開火已無法重建：
`logging_config.py` 只寫 stdout，運行期間沒有保留 log。本節的因果部分
因此是推論，不是直接觀測。

50 降到 4 相當於 46 次死亡，除以 1,264,115 次抓取等於每 27,481 次抓取
一個。這個比率是由結論反推出來的合理性檢查，與獨立等風險的指數存活曲線
一致，但它本身不構成獨立證據。

### 2.3.4 已排除為主因的假設

- **記憶體中無上限累積的狀態造成 GC 停頓**：已排除。本文件先前版本把它
  列為主要假設，量測之後並不成立。`_seen`、referrer 對應表、
  `RobotsCache` 中的 `RobotFileParser` 物件與 `crawler/ratelimiter.py` 三個
  以網域為 key、從不淘汰的 dict 確實只增不減（已逐一確認沒有淘汰路徑），
  但 event loop 層級的停頓會同時拉長 `elapsed_ms`，因為
  `fetcher.py` 的計時橫跨 await；而逐小時 p50 的上升幅度只有 1.29 倍，
  遠小於 9.2 倍。以視窗結束時的狀態量在本機重現，單次 GC 成本為毫秒級。

- **`write_checkpoint()` 阻塞 event loop**：成立但影響極小。它確實是同步
  呼叫，會在 event loop 執行緒上把整個 `_seen` 序列化成 JSON，成本隨資料
  成長。以視窗結束時的狀態量在本機重現，單次約 0.736 秒；視窗內共 576 次
  寫入，合計約 424 秒，佔 172,800 秒的 0.25%。本文件先前版本寫的「可量測
  的停頓共 67 段、加總 841 秒、單次最長 41 秒」在任何門檻下都重現不出來，
  且該算法量測的是完成紀錄的空窗——那是低吞吐量的結果，不是成因；該數字
  予以撤回。`output/metrics_log_clean.csv` 取樣器在整段視窗內的最大空窗
  為 9 秒。

- **每網域 1.0 秒間隔造成排隊**：固定成本，與衰減無關。閘門確實生效——
  同網域連續完成的間隔在 0.9–1.1 秒有明顯尖峰，第 1 小時有 39.9% 的配對
  落在該區間。但排隊在第 1 小時咬得更緊而非更鬆（長度 ≥2 的排空鏈平均由
  4.00 降到 2.73），方向與衰減相反。同網域連續請求時的平均等待約 0.87 秒，
  這是條件平均，不是每次迴圈的成本。

- **目標站台整體變慢**：確實發生，但量級不足。見 §2.3.2 的 996 個配對
  網域，1.29 倍無法產生 9.2 倍。

## 2.4 防爬蟲陷阱上限的實際效果

`--max-pages-per-domain` 上限（見
[01-system-design.md](./01-system-design.md) §1.5）在整段視窗內持續生效：
上限在入列時強制執行，`domain_page_counts` 不存在超過 20 頁的網域。視窗
結束時 `crawler_distinct_domains_total` 為 174,973。

## 2.5 資料限制

  - **「觸及網域」與「實際發出請求的網域」不是同一件事**：兩者相差
    6,845 個，那是只被 `robots.txt` 擋下、從未真正發出請求的網域。這正是
    `robots_blocked` 欄位（見
    [01-system-design.md](./01-system-design.md) §1.7）所要保留的證據；
    兩個數字分開列出，以免把「觸及」誤讀為「抓取」。

- **四個網域數字對應四個階段**：`crawler_distinct_domains_total`
  174,973 是曾被加入 frontier 的網域數（§2.4）；165,730 是視窗內留下紀錄
  的網域數；158,885 是實際發出過請求的網域數；至少成功回應過一次的網域
  為 138,898。前兩者相差 9,243，那是收工時仍排在佇列裡、還沒輪到的網域，
  與續跑無關。回答「48 小時爬了多少網站」時應採 138,898。
- **網域一律以 `urlparse(url).netloc` 計算**，因此 `www.x.com`、`x.com`
  與 `x.com:8080` 算三個不同網域；改以可註冊網域（eTLD+1）計算會得到明顯
  較小的數字。
- **本次視窗不是冷啟動**：運行以 `--resume` 接續先前的狀態，視窗開始時
  已帶有約 6,400–6,800 個網域。確切數字無法由 committed 的資料重建，因為
  未經裁切的 `output/metrics_log.csv` 不在版本控制內。
